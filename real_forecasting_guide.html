What real time-series forecasting actually is

Real forecasting is completely different from your Random Forest model. Instead of asking "given a budget, how much does IT spend?" — it asks "given what IT spent in January, February, March... what will it spend in July, August, September?" It learns from YOUR system's own history, not a Kaggle dataset.

The core concept
The black line is past actual spending from your DB. The purple dashed line is the forecast — where spending is heading based purely on your own historical trend. The band is the uncertainty range. No Kaggle dataset. No external model. Just your own data projecting itself forward.
Three methods you can use — from simplest to most powerful
Method 1
Linear Trend
Fits a straight trend line through your historical data and extends it. Simple, needs only 3+ months of data. Already available in numpy — no new library.
Easy3+ monthsNo install
Method 2
Facebook Prophet
Purpose-built for business time series. Handles seasonality, holidays, trend changes automatically. Best results with 6+ months. One pip install.

Method 3
Weighted Moving Avg
Averages recent months with more weight on recent data. Smooths noise and follows trend. Good middle ground between linear and Prophet.

All three of these live inside your existing Python FastAPI microservice — the one already running on port 8001. You don't need a new service. Just add new endpoints to the same main.py file.
Method 1 — Linear trend forecasting

The simplest real forecast. Fits a straight line through your historical monthly spending and extends it into the future. Uses only numpy which you already have installed.

How it works conceptually
Jan: ₱38,000    Feb: ₱41,000    Mar: ₱39,500    Apr: ₱43,000    May: ₱45,000    Jun: ₱44,500
Trend: roughly +₱1,300 per month
Jul forecast: ₱44,500 + ₱1,300 = ₱45,800
Aug forecast: ₱45,800 + ₱1,300 = ₱47,100
Dec forecast: ₱44,500 + (₱1,300 × 6) = ₱52,300
The actual code — add to main.py
from fastapi import FastAPI from pydantic import BaseModel import numpy as np from typing import List, Optional class TrendForecastRequest(BaseModel): # Historical monthly spending from your DB — in order Jan→current month historical_spending: List[float] # e.g. [38000, 41000, 39500, 43000, 45000, 44500] department: str fiscal_year: int = 2026 months_to_forecast: int = 6 # how many future months to predict class MonthForecastPoint(BaseModel): month_index: int # 1=Jan, 2=Feb... month_name: str predicted: float upper_bound: float # predicted + uncertainty lower_bound: float # predicted - uncertainty class TrendForecastResponse(BaseModel): department: str method: str monthly_growth: float # avg ₱ change per month forecasts: List[MonthForecastPoint] projected_eoy: float # sum of all remaining months MONTH_NAMES = ["JAN","FEB","MAR","APR","MAY","JUN", "JUL","AUG","SEP","OCT","NOV","DEC"] @app.post("/forecast/trend", response_model=TrendForecastResponse) def trend_forecast(req: TrendForecastRequest): data = np.array(req.historical_spending) n = len(data) if n < 2: raise HTTPException(422, "Need at least 2 months of historical data" ) # Fit linear trend: y=slope * x + intercept x=np.arange(n) slope, intercept=np.polyfit(x, data, 1) # Calculate uncertainty from residuals predicted_past=slope * x + intercept residuals=data - predicted_past uncertainty=float(np.std(residuals) * 1.5) # 1.5σ confidence band # Generate future months forecasts=[] projected_total=0.0 start_month_idx=n # 0-based index of next month for i in range(req.months_to_forecast): x_future=n + i predicted=float(slope * x_future + intercept) predicted=max(predicted, 0) # spending can't be negative month_idx=(start_month_idx + i) % 12 # 0-based forecasts.append(MonthForecastPoint( month_index=month_idx + 1, month_name=MONTH_NAMES[month_idx], predicted=round(predicted, 2), upper_bound=round(predicted + uncertainty, 2), lower_bound=round(max(predicted - uncertainty, 0), 2) )) projected_total +=predicted return TrendForecastResponse( department=req.department, method="Linear Trend (OLS)" , monthly_growth=round(float(slope), 2), forecasts=forecasts, projected_eoy=round(projected_total, 2) )
This endpoint takes your real reconciled expense data from the DB, fits a trend line, and returns predicted spending for the next N months with confidence bands. The purple forecast line on your chart comes directly from this output.

Method 2 — Facebook Prophet (most powerful)

Prophet was built by Facebook's data science team specifically for business time series forecasting. It automatically handles seasonality (spending patterns that repeat yearly), trend changes, and works well even with missing data. This is the industry standard for exactly your use case.

Why Prophet is better than linear trend for spending data
Linear trend
Assumes spending grows in a straight line forever. If your data has a seasonal dip in February and spike in December, it ignores both. Simple but less accurate.
Prophet
Learns that December always spikes, February always dips, and Q4 generally rises. Accounts for these patterns automatically. Much more realistic for organizational spending.
Prophet needs at least 6 months of historical data to be reliable. With less than 6 months, use Method 1 (linear trend) or Method 3 (moving average) instead. Prophet will still run with less data but the seasonal detection won't be meaningful.

from prophet import Prophet import pandas as pd @app.post("/forecast/prophet") def prophet_forecast(req: TrendForecastRequest): n = len(req.historical_spending) if n < 3: raise HTTPException(422, "Prophet needs at least 3 months of data" ) # Build the DataFrame Prophet expects # ds=date column, y=value column # Assume historical data starts from January of fiscal year dates=pd.date_range( start=f"{req.fiscal_year}-01-01", periods=n, freq="MS" # Month Start frequency ) df=pd.DataFrame({"ds": dates, "y" : req.historical_spending}) # Fit the model — Prophet automatically detects: # - Overall trend (is spending growing or shrinking?) # - Yearly seasonality (which months are always high/low?) # - Weekly seasonality (disabled — we use monthly data) model=Prophet( yearly_seasonality=True, weekly_seasonality=False, daily_seasonality=False, uncertainty_samples=500, # for confidence bands changepoint_prior_scale=0.05 # how flexible the trend can be ) model.fit(df) # Generate future dates to forecast future=model.make_future_dataframe( periods=req.months_to_forecast, freq="MS" ) forecast=model.predict(future) # Extract only the future predictions (not the fitted past) future_only=forecast.tail(req.months_to_forecast) forecasts=[] for _, row in future_only.iterrows(): month_idx=row["ds"].month - 1 # 0-based forecasts.append(MonthForecastPoint( month_index=month_idx + 1, month_name=MONTH_NAMES[month_idx], predicted=round(max(float(row["yhat"]), 0), 2), upper_bound=round(max(float(row["yhat_upper"]), 0), 2), lower_bound=round(max(float(row["yhat_lower"]), 0), 2) )) return TrendForecastResponse( department=req.department, method="Facebook Prophet" , monthly_growth=0, # Prophet doesn't expose a single slope forecasts=forecasts, projected_eoy=round(sum(f.predicted for f in forecasts), 2) )
Prophet's output is the same shape as the linear trend output — so your frontend chart code doesn't change at all. You just switch which endpoint the .NET controller calls. Start with linear trend now, swap to Prophet once you have 6+ months of data.
Method 3 — Weighted moving average

The middle ground. Instead of a straight trend line, it averages your recent months — but gives more weight to recent months because they're more relevant. If spending jumped in May and June, the forecast reflects that more than January's data does.

How weighting works
Historical: Jan ₱38k · Feb ₱41k · Mar ₱39.5k · Apr ₱43k · May ₱45k · Jun ₱44.5k
Weights applied (most recent = highest weight):
Jun × 6, May × 5, Apr × 4, Mar × 3, Feb × 2, Jan × 1 → sum of weights = 21
WMA = (44.5×6 + 45×5 + 43×4 + 39.5×3 + 41×2 + 38×1) / 21 = ₱43,450
Jul forecast = ₱43,450  (projected forward, adjusting for growth trend)
Code — add to main.py
@app.post("/forecast/moving-average") def moving_avg_forecast(req: TrendForecastRequest): data = req.historical_spending n = len(data) if n < 2: raise HTTPException(422, "Need at least 2 months of data" ) # Weighted moving average — recent months weighted higher weights=np.arange(1, n + 1, dtype=float) # [1,2,3...n] wma=float(np.average(data, weights=weights)) # Calculate trend from last 3 months (or all if fewer) window=min(3, n) recent=data[-window:] if len(recent)>= 2: trend = (recent[-1] - recent[0]) / (len(recent) - 1) else: trend = 0.0 # Uncertainty = std dev of recent data uncertainty = float(np.std(data[-min(6,n):]) * 1.2) forecasts = [] base = wma start_idx = n for i in range(req.months_to_forecast): predicted = max(base + trend * (i + 1), 0) month_idx = (start_idx + i) % 12 forecasts.append(MonthForecastPoint( month_index = month_idx + 1, month_name = MONTH_NAMES[month_idx], predicted = round(predicted, 2), upper_bound = round(predicted + uncertainty, 2), lower_bound = round(max(predicted - uncertainty, 0), 2) )) return TrendForecastResponse( department = req.department, method = "Weighted Moving Average", monthly_growth = round(trend, 2), forecasts = forecasts, projected_eoy = round(sum(f.predicted for f in forecasts), 2) )
The honest problem you need to understand

All three methods above are real, working forecasting algorithms. But they all share one requirement that you cannot skip:

Every single one of these methods requires historical spending data from YOUR system.

If NexaPlan is new and departments haven't reconciled expenses yet, there is no historical data to forecast from. You cannot forecast from zero data. No algorithm in the world can.
How much data each method needs
Linear Trend
Minimum 3 months of reconciled expense data. Usable but not very accurate.
3 months
Weighted Moving Avg
Minimum 3 months. Better than linear with 6+ months.
3 months
Facebook Prophet
Minimum 6 months for basic accuracy. 12+ months for seasonal detection. Best after a full year.
6 months
What this means for your system right now
If 0-2 months data
Cannot forecast yet. Show "Forecasting available after 3 months of spending data" message. Use ML model risk signals and committed proposals line only.
If 3-5 months data
Use linear trend or weighted moving average. Prophet won't be reliable yet. Forecast is early and rough but real.
If 6-11 months data
Switch to Prophet. It starts detecting seasonal patterns. Forecast becomes meaningfully accurate.
After 12+ months
Prophet is now highly accurate. It has seen a full year of your organization's patterns. This is when forecasting becomes your most powerful feature.
This is not a limitation of your system — this is how every financial management platform works. SAP, Oracle, QuickBooks all require historical data before forecasting activates. Your system is architecturally correct. It just needs time and real usage to accumulate the data that powers real forecasts.
